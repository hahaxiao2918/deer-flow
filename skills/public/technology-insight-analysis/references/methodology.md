# Static route-mapping methodology

## Route representation

Describe a route as an evidence-supported tuple: `{technical problem, system/component, mechanism, control variable, claimed outcome}`. Build the codebook before grouping. A patent can be `primary`, `secondary`, or `hybrid` in multiple routes; do not force exclusivity.

## Grouping and comparison

Start with label/evidence dimensions, then merge only when the mechanism and component relationship is substantively comparable. For each route preserve member PNs, evidence_ids, defining features, variants, counter-evidence, and unresolved boundaries. Outliers remain visible.

Applicant participation is the count/distribution inside the frozen corpus. It is not market share, patent-family strength, or commercial position. Report both raw counts and corpus-relative proportions with the corpus boundary beside them.

## Insight strength

Use `observed` for direct document patterns, `interpreted` for a defensible synthesis, and `hypothesis` for an explanation needing more evidence. Each insight lists evidence_ids, competing explanation, and coverage limitation. Static RouteMap statements are valid only at the corpus cutoff.

If a route cannot be assessed because relevant records or fields are missing, emit a structured search_gap_request to the Retriever rather than invoking discovery.
